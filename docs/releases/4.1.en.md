# MultiRoute Downloader 4.1

[Русский](4.1.ru.md) · [English guide](../en.md) · [Project overview](../../README.md)

This release adds persistent network-failure diagnostics and validates the LAN configuration used by the application's private gateway transport. Existing downloads, uploads, site profiles, queue controls, browser integration and checksum verification remain available.

## Network errors remain available after a retry

- A separate UTF-8 journal, `logs/network-errors.log`, records the time, selected gateway, server, failure stage and elapsed time. Native tunnel errors also include the resolved destination IPv4 and lwIP error code when available.
- Intermediate download failures include the job ID, segment number and byte range, even when a later attempt succeeds. The journal survives application restarts and eviction of older entries from the bounded on-screen history.
- At 4 MiB the journal rotates, keeping three archives. Existing journal entries retain the language used when they were written; the on-screen history can be rendered in the currently selected language.
- New diagnostic records exclude source URL paths, query strings, fragments, credentials, request headers and proxy response bodies. They retain the destination hostname needed to distinguish the original site from a redirected storage/CDN server.
- Local CONNECT failures now identify parsing, ARP, DNS, socket creation, binding or TCP establishment as the failing stage. A connection that closes before establishment is distinguished from an expired connection deadline.

These changes make a new failure diagnosable. They do not recover native details discarded by an older build, and they do not establish that every previously reported `Tunnel failed, got: 502` has been cured. A local CONNECT 502 and an HTTP 502 returned by an HTTPS origin are different failures.

## Subnet validation and changes to the computer's IP

- The selected interface's actual IPv4 mask is used. The computer, application virtual IP and every configured gateway must have usable, distinct host addresses in one subnet. Validation covers non-/24 networks such as /16, /23 and /25.
- The application virtual IP and gateway addresses must not be assigned to the computer. Network and broadcast addresses are rejected using the real mask.
- While the gateway component is running, it checks the selected interface again approximately every two seconds. A different computer IPv4 on the same physical interface, within the same subnet and with the same mask, leaves the application virtual IP, private TCP/IP stack and proxy ports in place. The observed change is logged.
- A subnet or mask change, inactive interface, changed adapter hardware identity or conflicting address stops the private transport and requires another network check. Verified download segments remain available for resumption.

MultiRoute does not set the computer's IP or change the OS routing table. It does not silently transfer a selected-gateway download through the system default gateway. The subnet check establishes local configuration consistency; each router still needs working Internet access for the virtual IP.

The interface now shows the observed computer IP, subnet, virtual IP and gateway count, with translated status text and a tooltip explaining the check. New messages are available in all twelve supported languages.

## API

`GET /api/v1/network` now includes `network_validation`, with `pending`, `valid` or `error` status and the available interface/subnet evidence. Reading it does not start the gateway component. `POST /api/v1/routes/inspect` checks a configured gateway and starts the component if necessary; it is an ARP/network check, not a speed test.

See the [network diagnostic guide](../network-diagnostics.en.md), [API examples](../../API.ru.txt) and [OpenAPI schema](../../openapi.yaml). The local API remains on `http://127.0.0.1:8765/api/v1` by default; the application virtual IP is not the API listen address.

## Installation and verification limits

Install the complete matching 4.1 package so that the Java application and platform gateway component are updated together. The native packages include Java:

| Platform | Installer |
| --- | --- |
| Windows 11 x64 | `MultiRoute-Downloader-4.1-Windows-x64-Setup.exe` |
| Apple Silicon, macOS 26+ | `MultiRoute-Downloader-4.1-macOS-arm64.pkg` |
| Intel, macOS 15+ | `MultiRoute-Downloader-4.1-macOS-x86_64.pkg` |

The matching verification report, `NATIVE-INSTALLER-TESTS.json`, is distributed alongside the installers on the release page; it is not included in the installed application's documentation. Check its source commit, package hashes and actual checks. The [platform guides](../en.md) describe prerequisites and security confirmations.

This is a prerelease. The application installers are unsigned; macOS packages are not Developer ID signed or notarized. Package and fixture checks do not prove operation on a particular user's computer. A real DHCP lease change during a live multi-router transfer has not been verified; the same-subnet behavior is covered with controlled interface snapshots. End-user installation/security dialogs and physical gateway WAN behavior require validation on the target systems.

The transport's existing public-IPv4/Ethernet requirements remain. Gateway-bound DNS still uses UDP A queries without TCP truncation fallback or separate CNAME continuation queries. IPv6-only sources and Wi-Fi-only/VPN-only transport are outside this mode. DNS, WAN availability or remote-server restrictions can still prevent a tunnel from being established.
